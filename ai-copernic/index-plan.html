Copernic Index Plan

Search the clouds you already pay for, crawl only what they can't reach, and put one connector in front of both.

Today the search page forgets your files when you close the tab. This plan makes it remember, in four steps. Each step ships something you can use and has a test that decides whether the next step is worth building.

Why a connector

What we know for certainA claude.ai page can't call your own server directly; the browser blocks it. It can call connectors, using your sign-in. So the only bridge from the search page to a persistent index is a connector. Built that way, the same index also works inside any Claude chat, with no extra work.

The four phases

Each phase ends with a test. If it fails, stop and rethink before building the next one.

  1. I2–4 days

    Search the clouds you already have start here

    No servers. The search page calls the Google Drive, Dropbox, Box and Microsoft 365 connectors you've already linked, all at once, and merges the results into one ranked list. Files you drop onto the page are saved in your browser, so they're still there next time.

    • One query goes out to every connected source at the same time; results arrive as each source answers.
    • Each result is labelled with its source; the same file stored in two places shows up once.
    • Ask Copernic answers from passages across all sources.

    Pass ifyou use it on at least 5 of 7 days for two weeks. If you don't, a persistent index won't change that.

  2. II1–2 weeks

    Crawl what the clouds can't reach

    One server running Elasticsearch and the Copernic crawler, with Tesseract OCR turned on. Point it at your disk, NAS, SSH and FTP folders. It re-checks every 15 minutes for new, changed and deleted files.

    • Server: 8 GB of memory is the practical minimum for Elasticsearch, with disk at about 1.5× the size of the extracted text.
    • Version check: the 2.9 crawler line works with Elasticsearch 6 and 7. For Elasticsearch 8, move to the 2.10 line.
    • Only build this if phase 1 showed you're missing files that live outside the clouds.

    Pass ifa full crawl finishes, and a file you edit can be found with its new text within 15 minutes.

  3. III1–2 weeks

    Put the Copernic connector in front of the index

    A small read-only connector (an MCP server) with three tools. search returns matching passages with the file, its location and a score. get_passage returns the full text of one passage. sources lists what's indexed and when each source was last crawled. Add it to claude.ai as a custom connector; the search page then lists it next to your cloud drives.

    • Sign-in is required. The connector uses a read-only Elasticsearch key and can never change or delete files.
    • It can run on Vercel, which you already use, because it keeps no state. Elasticsearch stays on the phase 2 server, reachable only over an encrypted connection.
    • Every search is logged with who ran it and when.

    Pass ifone query returns results from Google Drive and your NAS in one list in under 2 seconds, and a Claude chat can find a NAS file by name.

  4. IVlater

    Search by meaning, then add other people

    Add meaning-based search to the Elasticsearch index, so "late delivery penalties" finds a clause that says "2% credit per week". Then per-user permissions, so each person sees only the files they're allowed to see. Do this only if Copernic becomes a product for other people.

    Pass ifmeaning-based search beats keyword search on 20 real questions you write down in advance.

Decisions and how reversible they are

DecisionCallDoor
Start with cloud connectorsYes. Uses indexes that already exist and costs nothing to try.Reversible

Personal tool or productDecide before phase 4. It decides whether you need user accounts, permissions and billing.One-way

What we are not doing

  • No new file types. Coverage isn't what's holding this back; keeping files between visits is.
  • No separately hosted website for the search page. claude.ai already handles sign-in, connectors and Claude.
  • No meaning-based search before the index keeps files. Ranking a temporary index better doesn't help anyone.
  • No accounts for other people before you use it daily. If you don't use it every day, nobody else will.
  • No custom OCR engine. Tesseract in the crawler handles bulk scans; Claude handles hard photos.

What would sink it

Indexing everything before knowing what you actually search for. Running Elasticsearch on too small a server and spending weekends on it. Showing the same file three times because it sits in Drive, Dropbox and the NAS; fix this by matching on file content. Most of all, an index of private documents reachable without a sign-in.

Three answers I need before phase 2

  1. Where do the files you search for most actually live?If it's almost all cloud drives, phase 1 may be the whole job.
  2. Is this for you, or for customers?This decides phase 4 and whether security work starts now or later.
  3. Roughly how many files, and how many GB?This decides the server size and how long the first crawl takes.
